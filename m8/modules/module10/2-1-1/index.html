    2-1-1. Pod 실습¶

    실습 목표¶

    • kubectl run과 YAML로 Pod를 생성하고 차이를 이해한다.
    • 멀티 컨테이너 Pod 구조를 실습한다.
    • Label의 역할과 --show-labels 옵션을 익힌다.

    공식 문서 참고¶

    • Pod 공식 문서
    • kubectl 치트시트

    0) 실습 폴더 준비¶

    앞으로 2일간 작성할 YAML 파일을 한곳에 모아 관리합니다. 아래 순서로 폴더를 만들고, day1 폴더에서 터미널을 열어 실습을 시작합니다.

    mkdir k8s-lab
cd k8s-lab
mkdir day1, day2
cd day1

    mkdir k8s-lab
cd k8s-lab
mkdir day1 day2
cd day1

    이후 모든 실습 파일은 day1 폴더 안에 저장합니다. Day 2 실습이 시작되면 day2 폴더로 이동합니다.

    1) kubectl run으로 Pod 빠르게 생성¶

    YAML 없이 명령어 한 줄로 Pod를 만들 수 있습니다.

    kubectl run nginx-pod --image=nginx:1.25

    상태 확인:

    kubectl get pods
kubectl get pods -o wide    # Pod IP 포함

    dry-run으로 YAML 미리 보기¶

    --dry-run=client -o yaml 옵션을 붙이면 실제로 생성하지 않고 YAML만 출력합니다. YAML 작성이 익숙하지 않을 때 시작점으로 활용할 수 있습니다.

    kubectl run test --image=nginx:1.25 --dry-run=client -o yaml

    출력 예시:

    apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: test
  name: test
spec:
  containers:
  - image: nginx:1.25
    name: test
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always

    dry-run이 자동으로 채워주는 필드들의 의미는 다음과 같습니다.

    필드 의미
    resources: {} CPU·메모리 요청/제한 없음 (비어있음). 나중에 requests·limits를 직접 채워 넣습니다
    dnsPolicy: ClusterFirst 클러스터 내부 DNS(CoreDNS)를 먼저 조회하는 기본 정책
    restartPolicy: Always 컨테이너가 종료되면 항상 재시작하는 기본 정책
    status: {} 현재 실행 상태 정보. 생성 전이라 비어있으며, 실제 배포 후 K8s가 자동으로 채움

    이 출력을 파일로 저장해서 편집하면 됩니다.

    kubectl run test --image=nginx:1.25 --dry-run=client -o yaml > pod-test.yaml

    2) YAML로 Pod 생성¶

    pod-nginx.yaml 파일을 확인합니다.

    apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
    env: lab
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80

    kubectl apply -f pod-nginx.yaml
kubectl get pods
kubectl describe pod nginx-pod

    describe 출력에서 확인:

    • Status: Running
    • IP: Pod에 할당된 내부 IP
    • Labels: 부여된 label 목록
    • Events: 이미지 pull → 컨테이너 시작 과정

    로그 확인¶

    kubectl logs nginx-pod
kubectl logs nginx-pod -f    # 실시간 스트리밍

    Pod 내부 접속¶

    -- 는 kubectl 옵션의 끝을 알리는 구분자입니다. 이후에 오는 bash는 kubectl이 아닌 컨테이너 안에서 실행할 명령어로 전달됩니다. Docker의 docker exec -it nginx-pod bash와 달리 kubectl은 자체 옵션과 컨테이너 명령어를 --로 분리합니다.

    kubectl exec -it nginx-pod -- bash
# 컨테이너 내부
nginx -v
curl localhost
exit

    curl 이미지로 Pod 간 통신 확인¶

    curlimages/curl 은 curl 명령어만 포함된 초경량 이미지로, 클러스터 내부에서 HTTP 통신을 빠르게 테스트할 때 사용합니다.

    nginx-pod의 IP를 확인한 뒤, curl 이미지를 실행해 해당 IP로 요청을 보냅니다.

    kubectl get pods -o wide    # nginx-pod의 IP 확인 (예: 10.1.0.5)

    kubectl run curl-test --image=curlimages/curl:latest --restart=Never -it --rm \
  -- curl http://10.1.0.5

    nginx 응답 HTML이 출력되면 성공입니다. --rm 옵션으로 종료 시 Pod가 자동 삭제됩니다.

    Pod 삭제 후 IP 변화 관찰¶

    kubectl delete pod nginx-pod
kubectl apply -f pod-nginx.yaml
kubectl get pods -o wide    # 새 IP가 할당됨을 확인

    포인트: Pod를 재생성하면 IP가 바뀝니다. 그래서 Service가 필요합니다.

    3) 멀티 컨테이너 Pod¶

    하나의 Pod에 컨테이너를 여러 개 넣을 수 있습니다. 같은 네트워크와 스토리지를 공유하므로 localhost로 서로 통신합니다.

    command 필드란?¶

    command는 컨테이너가 시작될 때 실행할 명령어를 직접 지정하는 필드입니다. Docker의 ENTRYPOINT에 해당합니다.

    필드 Docker 대응 설명
    command ENTRYPOINT 실행할 명령어 (이미지 기본값 덮어씀)
    args CMD 명령어에 전달할 인자

    command를 지정하지 않으면 이미지에 정의된 기본 명령어가 실행됩니다. 아래 예시에서 sidecar 컨테이너는 이미지 기본 동작 대신 sh -c "while true; ..." 쉘 스크립트를 실행합니다.

    command: ["sh", "-c", "while true; do echo $(date) $(curl -s localhost); sleep 5; done"]
#          ↑실행파일   ↑sh에 전달되는 인자: 5초마다 localhost(=nginx)에 curl 요청

    VS Code로 파일 작성하기

    지금부터는 YAML 파일을 직접 작성합니다. 앞서 만든 k8s-lab/day1 폴더를 VS Code로 열고, 여기서 파일을 생성해 실습합니다.

    code "$HOME\k8s-lab\day1"

    code ~/k8s-lab/day1

    VS Code가 열리면 왼쪽 탐색기에서 새 파일 아이콘을 클릭해 파일을 생성합니다.

    복사·붙여넣기 금지 — 손으로 직접 입력하세요

    pod-multi.yaml은 이 실습에서 처음으로 직접 작성하는 YAML 파일입니다. 복사·붙여넣기 대신 한 줄씩 손으로 타이핑하면서 들여쓰기 구조와 각 필드의 위치를 몸으로 익혀두세요. YAML은 들여쓰기가 곧 구조이므로, 직접 쳐보는 것이 가장 빠른 학습 방법입니다.

    apiVersion: v1
kind: Pod
metadata:
  name: multi-pod
  labels:
    app: multi
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
    - name: sidecar
      image: curlimages/curl:latest
      command: ["sh", "-c", "while true; do echo $(date) $(curl -s localhost); sleep 5; done"]

    kubectl apply -f pod-multi.yaml
kubectl get pods    # READY 2/2 확인

    각 컨테이너 로그를 따로 확인합니다.

    kubectl logs multi-pod -c nginx      # nginx 컨테이너 로그
kubectl logs multi-pod -c sidecar    # sidecar 컨테이너 로그

    sidecar가 localhost로 nginx에 접근하여 응답을 받는 것을 확인합니다.

    특정 컨테이너 내부 접속:

    kubectl exec -it multi-pod -c nginx -- bash

    4) Label과 --show-labels¶

    Label은 K8s 리소스에 붙이는 키-값 태그입니다. Deployment가 Pod를 선택하거나 Service가 트래픽을 보낼 대상을 찾을 때 label을 기준으로 합니다.

    label 확인¶

    kubectl get pods --show-labels

    출력 예시:

    NAME        READY   STATUS    RESTARTS   AGE   LABELS
nginx-pod   1/1     Running   0          2m    app=nginx,env=lab
multi-pod   2/2     Running   0          1m    app=multi

    label 기준으로 필터링¶

    -l 옵션으로 특정 label을 가진 Pod만 조회할 수 있습니다.

    kubectl get pods -l app=nginx
kubectl get pods -l env=lab
kubectl get pods -l app=nginx,env=lab    # 두 조건 모두 만족

    label 추가 / 변경 / 삭제¶

    kubectl label pod nginx-pod version=v1          # label 추가
kubectl label pod nginx-pod env=production --overwrite   # label 변경
kubectl label pod nginx-pod version-            # label 삭제 (키 뒤에 - 붙임)
kubectl get pods --show-labels                  # 변경 결과 확인

    label을 처음부터 붙여서 Pod 만들기¶

    Pod를 생성할 때부터 label을 지정하는 두 가지 방법을 익혀둡니다.

    방법 1 — kubectl run에 --labels 옵션 사용

    kubectl run labeled-pod --image=nginx:1.25 --labels="app=web,env=dev"
kubectl get pods --show-labels

    방법 2 — dry-run으로 YAML을 뽑아 label 추가

    먼저 dry-run으로 기본 YAML을 파일로 저장합니다.

    kubectl run labeled-pod2 --image=nginx:1.25 --dry-run=client -o yaml > pod-labeled.yaml

    저장된 pod-labeled.yaml을 VS Code에서 열어 metadata.labels 항목에 label을 추가합니다.

    apiVersion: v1
kind: Pod
metadata:          # ← 리소스의 이름·네임스페이스·label 등 식별 정보
  name: labeled-pod2
  labels:          # ← label은 metadata 바로 아래에 key: value 형태로 작성
    app: web       #   dry-run이 자동 생성한 run: labeled-pod2 는 지우고 아래 3줄로 교체
    env: dev
    version: v1
spec:
  containers:
    - name: labeled-pod2
      image: nginx:1.25

    kubectl apply -f pod-labeled.yaml
kubectl get pods --show-labels

    label 위치 정리

    위치 역할
    metadata.labels Pod 자체에 붙는 label — 다른 리소스가 이 Pod를 선택할 때 사용
    spec.template.metadata.labels Deployment·ReplicaSet이 관리할 Pod 템플릿에 붙는 label
    spec.selector.matchLabels Deployment·ReplicaSet이 어떤 label을 가진 Pod를 관리할지 지정

    지금은 Pod 단독 실습이므로 metadata.labels만 사용합니다. Deployment에서는 세 위치를 함께 맞춰야 하므로 2-1-2에서 다시 살펴봅니다.

    정리 (리소스 삭제)¶

    kubectl delete -f pod-nginx.yaml
kubectl delete -f pod-multi.yaml

    핵심 정리¶

    개념 설명
    Pod K8s에서 배포 가능한 가장 작은 단위, 컨테이너를 1개 이상 포함
    멀티 컨테이너 같은 Pod 내 컨테이너는 localhost로 통신, 스토리지 공유
    Label 리소스에 붙이는 키-값 태그, Service·Deployment의 대상 선택 기준
    Pod IP 재생성 시 변경됨 → Service가 필요한 이유

    트러블슈팅¶

    증상 확인 사항
